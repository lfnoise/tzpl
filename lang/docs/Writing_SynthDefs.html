Writing SynthDefs

A synthdef is a description of an audio signal-flow graph, written as ordinary Tzopilotl code, that the synthdef compiler turns into an optimized native plugin the audio engine can instantiate as nodes. This guide covers the whole authoring surface: the graph-construction model, signal rates, element types, channel counts and broadcasting, controls and note parameters, delays, buffers, control flow, polyphonic voicers, and a reference for the three modules involved — synthdef (the building blocks), common_ugens (unit generators built from them), and filters (biquad filters).

For a task-oriented introduction with engine and scheduling recipes, see the Music Cookbook. The compiler, synthc, is itself written in Tzopilotl (lang/modules/synthc/ in the repository); its design — block processing, parameter groups, recurrence analysis — is described in devplans/BLOCK_ENGINE_PLAN.md.

1. How SynthDefs Work

A synthdef is written as a Tzopilotl function of no arguments returning S (short for SignalExpr). The function does not process audio when it runs. Instead, it runs once at definition time to build a graph: every operation on an S value — +, sinosc, lag, outlet — appends a node to the graph under construction and returns a new S referring to it. The finished graph is handed to the synthdef compiler, which analyzes it (rates, types, channel counts, common subexpressions, SIMD) and generates a native .dylib plugin that the engine loads and can instantiate as nodes.

your synth fn (.x) —runs once→ SignalGraph —defSynthX→ compiled .dylib plugin
                                                        ↓
                                       engine loads it; newNode() makes instances

Two consequences of this staging model are worth internalizing:

  • Every unit generator is a graph macro. All of common_ugens.x and filters.x is ordinary Tzopilotl code that manipulates S values. Calling lpf(x, 800) inlines a biquad's worth of nodes into your graph. There is no overhead for building abstractions out of small functions — the compiler sees only the resulting flat graph and optimizes it as a whole (constant folding, common-subexpression elimination, rate factoring).
  • Ordinary language features are compile-time constructs. A Tzopilotl for loop, array comprehension, or recursive function that builds signal expressions unrolls into the graph. Use them freely to generate banks of oscillators, filter cascades, etc. (For a loop that must exist in the generated code, see for_.)

A minimal synthdef, defined and played:

import synthdef.*;
import synthc.compile.*;   -- provides defSynthX, the production compile path
import common_ugens.*;

fn beep() S =
    [330.0, 331.0] sinosc          -- 2-channel sine (slightly detuned)
    * (1.0 lfimp decay(0.25))      -- 1 Hz impulse -> exponential decay envelope
    * 0.2
    |> outlet;                     -- the graph's output sink

beep defSynthX("beep") await;      -- compile + load into the engine
"beep" play;                       -- make a node and connect it to audio out

The compile itself runs in the background, so any music already playing keeps running while clang works. The await waits until the def is loaded into the engine. play waits on its own for a compile of that name still in flight, so the example would work without it; the await is what makes a following newNode in a hand-built bundle, or a ui.control(node, ...), safe as well, and it surfaces a failed compile where you can see it. When you re-evaluate a defSynthX call for a def that is already playing you can drop the await: players keep using the old version and switch to the new one the moment it finishes loading.

Synthdef code leans on two pieces of Tzopilotl syntax used heavily below: the space-separated pipeline (x sinosc sq is sq(sinosc(x))) and the |> pipe operator, which forwards the whole expression to its left into the function on its right. Many ugens are written with untyped parameters; they are generic over anything convertible to a signal (see §3).

2. The Signal Type: Rate, Element Type, Channels

Every expression in the graph has a signal type with three components, inferred by the compiler — you rarely write any of them explicitly:

ComponentWhat it isValues
rateWhen the expression is computed constant, init, reset, block, audio
element typeThe numeric type of each channel value i32, i64, f32, f64
shapeHow many parallel values (channels) it carries per sample, arranged in up to 4 dimensions any count: 1, 2, 3, …; or a matrix such as 2×3

2.1 Signal rates

The engine runs every node a block of samples at a time (64 by default). A compiled synth computes the whole block in one call, so it can run several samples or several channels in one vector instruction. Your graph still describes one sample: an audio-rate value has a new value every sample, d(1) is the previous sample (§9), and an input set or a note started mid-block takes effect at its exact sample. Blocks only change how much work is skipped.

Rates say how often a value needs to be recomputed. From slowest to fastest:

RateWhen computedTypical examples
Rate.constantAt compile time; folded away entirely Literals, arithmetic on literals
Rate.initOnce, when a synth instance is allocated fs(), T(), random values with rate: Rate.init, delay allocation
Rate.resetOnce per note-on (inside a voicer; once at init otherwise) Per-note setup: sample bank lookups (§10), per-note random values with rate: Rate.reset
Rate.blockOnly when one of its inputs has changed; every sample while any of them moves Math derived only from controls (control(...) and the other specced inputs of §7), note parameters (noteParam(...)), and slower values. The compiler places it; you never declare it.
Rate.audioEvery sample Oscillators, filters, anything downstream of an audio signal

Inputs are signals. A synth has no separate “controls”: every parameter is an input port, and every input is a signal. An input nothing is connected to holds a value (its spec's init, else 0) until you set, ramp, or patch it (§7). Math that depends only on controls, note parameters and slower values is a parameter group, placed at block rate. At the start of each block the compiled synth asks the engine, for each input a group reads, whether it was changed and whether it is constant over this block. It skips the group when none of its inputs changed, recomputes it once when one was set to a new value, and computes it every sample while one is ramping or connected to a moving signal. So a knob that sits still costs nothing, and the same synth can be driven from an audio-rate signal with no recompile. The check is per input: setting one element of a multichannel control recomputes every group that reads that control.

A plain inlet (one without a spec) is treated as an audio signal, since it is usually patched from another node; math on it runs every sample. Inside if_/switch branches (§11) and spectral bodies (§13), block-rate math is computed every sample too.

Note parameters are columns of the voiced synth's notes input (§12), so they behave the same way: math derived purely from note parameters (a frequency-dependent filter coefficient, a velocity curve) is recomputed per voice when the note's parameters change, not every sample. gate() is column 0 of the same input, set by the engine at note-on and note-off; its edges land on the exact sample, so adsr and tr over it see a genuine one-sample edge.

Rate propagation. The rate of a derived expression is the maximum of its inputs' rates. Multiplying an audio-rate oscillator by a control gives an audio-rate result; adding two constants gives a constant that never reaches the generated code at all. You do not choose rates for computed expressions — the compiler infers them, and its rewrite passes actively factor low-rate subexpressions out of audio-rate code so that, e.g., freq * 2 * pi * T() driven by a control is recomputed only when the control changes.

The places you do state a rate are source nodes whose rate is a free choice — the random generators (§8) take a rate argument. frand(100, 600, 8, Rate.init) picks 8 random frequencies once per synth instance; with the default Rate.audio it would be white noise.

Rate values are ordered (<, <=, min, max are defined on them) with constant < init < reset < block < audio.

2.2 Element types

Each signal's per-channel values have one of four concrete numeric types: i32, i64, f32 (the usual audio sample type), and f64. During graph construction, types are tracked as constraint sets (NumType bit-sets such as ANY_NUM, ANY_FLOAT, ANY_INT) and iteratively narrowed to a concrete type by the compiler's type inference:

  • Integer literals and integer-valued float literals enter the graph as ANY_NUM — they adapt to whatever consumes them. 440 becomes an f32 when fed to sinosc and an i64 when used as a bit mask.
  • Non-integer float literals are ANY_FLOAT.
  • Transcendental functions (sin, exp, …) constrain their operand to float; bit operations (&, <<, popCount, …) constrain theirs to integer.
  • When two types meet in a binary operation, the common type is the wider one, floats winning over ints (i32+f32 → f32, f32+f64 → f64). The compiler converts the narrower operand for you: an f32 oscillator added to an f64 phase is computed in f64. The same holds for comparisons and for the two values of select2. Other places that join signals — a delay's write and its reads, the branches of if_ — still need one type, so cast there.
  • A cast on a literal sticks: 1.5 f64 stays f64 even when the compiler folds it into another constant.

When you need a specific width, use the cast operators i32, i64, f32, f64 (postfix, like any ugen). The main practical uses:

-- Phase accumulators: accumulate in f64 for precision, read out in f32.
fn phasor(fm AsSignal) S {
    let phase = delayVar();
    phase <- frac(phase(1) + fm f64 * T() f64);
    phase(1) f32
}

-- Integer arithmetic: force a counter to integer before %.
c <- (c1 + t) i32 % n;

2.3 Channel counts

A signal carries chans parallel values per sample — its channels. A plain oscillator is 1-channel; [330.0, 331.0] sinosc is a 2-channel signal (two sines computed in lockstep). Multichannel expansion is how you get stereo, oscillator banks, and SIMD-friendly parallelism.

Channel counts are exact: a 3-element vector is a 3-channel signal. A signal may also have a shape of up to 4 dimensions (a Shape, row-major, the last dimension varying fastest); channel c is the row-major flattening, and a plain channel count is a 1-dimensional shape. shape([2, 3]) (or matrix(2, 3)) is a 2×3 shape of 6 channels. The functions that create multichannel signals — inlet, control, fill, … — take either an Int channel count or a Shape; a count of 1 is a scalar.

A shape has a rank, its number of dimensions: a scalar is rank 0, row(n) rank 1, matrix(r, c) rank 2, cuboid(p, r, c) rank 3. The rank is part of the shape, so matrix(1, n) (one row) and row(n) have the same channels but are different shapes. The dimensions are the signal's axes, numbered from the outermost, starting at 0, as in NumPy; negative numbers count from the last axis, so -1 is always the columns. The constants cols (−1), rows (−2) and planes (−3) name them at any rank. The shape operations of §5 work along an axis.

2.4 Channel broadcasting

When a binary operation combines signals of different shapes, each dimension of the result is the least common multiple of the inputs' sizes in that dimension, and each input is repeated cyclically to fill it: along each dimension, index i of the result reads index i mod size of the input. A 2-channel signal against an 8-channel one repeats its pair four times; a 2-channel signal against a 3-channel one gives 6 channels, each input cycling. A 1×3 row against a 2×1 column gives a 2×3 matrix. Shapes of different ranks line up from their last axes, so a row of 3 against a 2×3 matrix applies to each of its rows.

-- scalar against stereo: the scalar applies to both channels
[330.0, 331.0] sinosc * 0.2              -- 2 chans

-- stereo against 8 channels: the [-1, 1] detune alternates across all 8
let detune = [-1, 1] vec;                -- 2 chans
let freqs = exprand(100, 600, 8, Rate.init) + detune;   -- 8 chans

-- unary ops and ugens are per-channel: this filters both channels
[200, 300] smoothSaw(4) lpf(1200)

Broadcasting composes with every ugen in the library, because ugens are built from these same per-channel operators — feeding a 2-channel frequency into sinosc gives a stereo oscillator whose internal phase accumulator is itself 2-channel. Delays declared inside a ugen widen the same way, so [0.2, 0.3] vec of delay times gives two independent delay lines.

Reducing width back down. Broadcasting only ever widens. To mix channels down, use the reductions in §5: sum mixes everything to 1 channel, and sum(axis) mixes along one axis. Give a bank the shape of its output to mix it to stereo: a bank of n×2 oscillators, sum(0), is a stereo pair, and so is a voicer of stereo voices (voices×2).

5. Shape Operations

These rearrange and reduce a signal's channels by its shape (§2.3). Each works along one axis, the last by default, so on a 1-dimensional signal they act on its channels in order. axis is 0 for the outermost, negative from the last (cols = −1, rows = −2, planes = −3); an axis the signal does not have is a compile error. A scalar counts as a row of one. Result shapes, and errors (an axis out of range, shapes that disagree off the axis, a reshape that does not divide), are found when the synth is compiled.

The rearranging operations — take, drop, stride, stutter, ncyc, slice, rotate, reverse, transpose, reshape — are views: they compute nothing. Each output channel is one channel of the source, chosen when the synth is compiled, and the operations that consume the view (arithmetic, ugens, other views, sum and the other reductions) read the source channels in the rearranged order, with no copy. A view is stored as a copy only when it has several consumers, when at, put or join reads it, or inside a voicer's voice body. A slice offset or rotate amount that is a signal rather than a constant picks the source channel while the synth runs: each element is read from its current source position, still with no copy. join and stack copy their operands into the result; reduce and scan compute it.

-- 16 random-frequency sines as 8 per side: an 8x2 bank, summed over
-- axis 0 (the 8) to stereo
fn shimmer() S {
    let freqs = exprand(200, 2000, 16, Rate.init) reshape([8, 2]);
    freqs sinosc sum(0) * 0.05 |> outlet
}

-- 16 random sine plinks, each randomly panned, mixed to stereo.
-- pandust(density, 16) is a 2x16 matrix (row 0 left, row 1 right); the 16
-- frequencies line up with its columns, and sum(cols) mixes each side.
fn dustCloud() S {
    let freqs = exprand(100, 5000, 16, Rate.init);
    let ticks = pandust(3/16, 16) decay2(0.004, 0.2);
    ticks * freqs sinosc |> sum(cols) outlet
}

7. Inputs and Controls

A synth's parameters are its inputs. There is no separate kind of “control” port: a control is an input port that carries a ControlSpec — an f32 input like any inlet, plus the range, initial value and widget kind a UI needs. Until something sets or connects it, it holds its spec's init. Because it is an ordinary input it can be stepped, ramped, crossfaded, fired as a one-sample impulse, or connected to another node's output, and a multichannel control can be set one element or one region at a time. Every change lands on its exact sample, even in the middle of a block. Only the math that depends on a changed control recomputes (§2.1).

Set inputs from Tzopilotl with the audio_engine bridge. Each call names the input by name or by index, and takes one value or an array of values, which repeats cyclically over the channels it addresses. They are bundle commands: put them between begin() and sched(silo) (or go), like newNode and connect, and they take effect when the bundle does. The app's UI can also generate widgets from controls — the spec and kind determine the widget (see Live Controls and Notebooks).

setInputBox(node, port, offset, extent, values, rampTime) A rectangular region of a shaped input, given by its corner and size in each dimension (an extent of 0 runs to the end).

begin(); setInput(n, "cutoff", 4000.0, 2.0); sched(0);          -- open the filter over 2 s

ControlSpec and warps

struct ControlSpec { lo Float, hi Float, init Float, warp ControlWarp }

enum ControlWarp { linear, exponential, step Float, signedSquare, cubed }

The spec gives the control's range, initial value, and warp — the curve a UI uses to map slider position to value (exponential for frequencies and gains, step(sz) for quantized values, signedSquare / cubed for finer resolution near zero). The warp does not change what your graph receives; it shapes the widget. The shorthands lspec(lo, hi, init) and espec(lo, hi, init) build a linear or exponential spec.

A control can also follow a signal: connect another node's output into it and it changes sample by sample. The math that reads it then runs every sample, and goes back to running only on changes once the control is disconnected and holds still.

Smoothing. A plain setInput is a step. For anything audible (gains, frequencies, filter cutoffs), either ramp the change (setInput(node, "gain", 0.5, 0.05)) or smooth the control with lag in the graph to avoid zipper noise. This is the standard output-gain idiom used by the examples: 
fn gainOutlet(x S) S {
    let gain = control("gain",
        ControlSpec{0.001, 1.0, 0.2, ControlWarp.exponential}) lag(0.1);
    x * gain |> outlet
}

Shared input: the mouse without messages

An input change is a message: it is bundled, scheduled, and delivered to one node. For values that change continuously and matter to every playing synth — the mouse position — the engine keeps a small shared-input table instead: the app writes it in the background (~60× a second for the mouse), and any graph reads it at audio rate with sharedIn. -- theremin: x = pitch, y = amplitude; every instance follows the mouse
fn theremin() S =

From the language side, setSharedInput(slot, value) writes a free slot and getSharedInput(slot) reads one back (audio_engine module) — a lightweight channel for any continuously varying value that would otherwise be a stream of setInput messages. 9. Delays and Feedback

A DelayVar is the graph's memory primitive: a ring buffer with one writer and any number of readers. Everything stateful — one-sample feedback, filters, envelopes, comb delays, phase accumulators, counters — is built on it.

API

Feedback

Reads at index ≥ 1 see previous samples, so a delay can be read and written in the same graph — that is how feedback works. The canonical one-pole filter:

fn onepole(x S, a AsSignal) S {
    let y = delayVar();
    y <- x + a * (y(1) - x)     -- y[n] = x + a*(y[n-1] - x); the write is the result
}

Since write returns the written value, the whole function body is both "update the state" and "the output". The unit-delay ugens z1 / z2 (§15.11) package the common cases: x z1 is x delayed one sample.

A delay declared with a multichannel writer widens per channel — each channel gets its own line. Delay times in seconds must be converted: delayTime * fs() is the read index in samples (see comb in §15.14 for the full pattern).

-- variable-delay chorus voice: 0..10 ms modulated cubic read
fn chorusTap(x S, rate AsSignal) S {
    let maxSamps = 0.01 * fs();
    let d = delayVar(maxSamps);
    d <- x;
    d(rate sinosc uni * maxSamps)      -- d(S) = vread, cubic by default
}

d(0) is the written signal itself, so it must come after the write in your code; reading it first would be feedback with no delay, which has no value, and is an error. A variable read whose delay time goes below 0 reads at 0.

Feedback runs in blocks, with per-sample results

A loop through a delay is a recurrence: each sample depends on earlier ones. The engine runs the synth a block at a time, but you still get the per-sample definition you wrote. The compiler finds each loop, classifies it, and picks a form that computes a whole block with the same values:

  • Running sums and wrapped accumulators (phasor and the oscillators built on it, counters): a running sum across the block, several samples at a time.
  • Linear filters whose coefficients come from controls or note parameters (onepole, lag, the biquads, ring, leakdc): a matrix form that steps the filter's state a block at a time, rebuilt only when a control changes. While a coefficient is ramping or connected to a moving signal, the same filter switches, per block, to the plain loop (or, for a one-pole, a running form over the block); the state carries over exactly.
  • Everything else (envelopes such as adsr, nonlinear feedback, filters with audio-rate coefficients): a loop a sample at a time over just the loop's own nodes, with everything outside it computed for the whole block. With 4 or more channels or voices, 4 run side by side.

The block forms round differently from a sample-at-a-time loop, by about 2×10−5 relative in f32 and 10−14 in f64. That is inaudible, but where a fed-back value drives a decision (a gate threshold, a sequencer step, a quantizer, a delay time, a very resonant filter) the difference can grow. To compile every loop in plain sample order — for a reference render to compare against — start the app with the environment variable TZPL_STRICT_RECURRENCES=1; it applies to every synth compiled while it is set. To see which form each loop got, print the graph's analysis: each CYCLE line is followed by its CLASS and STRATEGY.

-- prints one CYCLE per feedback loop: here the phasor inside sinosc
-- (a scan) and the lpf (a block state space)
fn tone() S = 220 sinosc lpf(1000) * 0.1 |> outlet;
makeGraph(tone) analysisDump("tone") println;

Delay lines are sized for the block automatically. A delay with no feedback (a chorus, a granulator) is written for the whole block first and then read several samples at a time; a feedback delay whose reads stay at least a block behind its write head (a long echo) is computed that way too.

Feedback between nodes

Feedback inside one synth is always written with a delayVar. Between nodes you can also connect outputs into inputs so that they form a cycle — a node into itself, or around a chain. The engine finds each cycle and runs it in one of two modes, chosen per silo with feedbackMode (from audio_engine):

  • FeedbackMode.feedbackSample (the default): the cycle's nodes run a sample at a time, and the connection that closes the cycle delivers its source's previous sample — a one-sample loop. Each node pays its per-call setup every sample, so a cycle costs several times what the same nodes cost in a chain.
  • FeedbackMode.feedbackBlock: the nodes run whole blocks and the closing connection is a block late (64 samples by default) — cheap, as in SuperCollider, and audibly different for tight loops.

Nodes outside cycles run in blocks either way.

import audio_engine.*;

-- a sine whose frequency is modulated by its own output
fn selfFM() S {
    let fb = inlet(FLOAT32, 1, "fb");
    sinosc(220 + fb * 1500) * 0.2 |> outlet
}
selfFM defSynthX("selfFM") await;
let n = "selfFM" play;                          -- a plain sine at first
begin(); connect(n, 0, n, 0); sched(0);        -- its output into its own input

feedbackMode(0, FeedbackMode.feedbackBlock);    -- the loop a block late: a different sound
feedbackMode(0, FeedbackMode.feedbackSample);   -- back to the default

10. Sample Buffers

A BufferVar is a slot for an externally provided block of sample data — a loaded sound file, a wavetable, recorded audio. Unlike delays, buffer contents are owned by the engine and can be swapped at runtime without recompiling the synth. Buffers are multichannel; frames are indexed from 0, buffers may be any length (no power-of-two requirement), and an out-of-range index wraps cyclically at the buffer's actual frame count — a 100-frame buffer read at index 100 yields frame 0. (Delay lines, which are ring buffers, keep their internal power-of-two masks.)

Graph-side API

Filling buffers from the engine

After creating a node, bind data to its buffer slots with the audio_engine bridge: loadBuffer(nodeID, bufID, path) loads an audio file (read on the non-real-time side, swapped in sample-accurately), fillBuffer(nodeID, bufID, numChans, data) pushes a computed [Float] (channel-concatenated: data[c*frames + i], so a single-channel buffer is just the sample array — e.g. a wavetable built with the ifft builtin or the wavetables module), and resizeBuffer(nodeID, bufID, numChannels, length) allocates an empty buffer for recording. All three require an active begin() bundle. Until a buffer is bound, reads return 0. The plugin exports its buffer slots (name, element type, expected channels) so browsers and tools can inspect them.

-- one-shot sample player: trigger restarts the playhead
fn samplePlayer() S {
    let buf = bufferVar();
    let t = trigger("play");
    let speed = control("speed", ControlSpec { lo: 0.25, hi: 4.0, init: 1.0, warp: ControlWarp.exponential });
    let pos = delayVar();
    let newPos = select2(t > 0, 0, min(pos(1) + speed, buf length f32));
    pos <- newPos;
    buf vread(newPos, Interpolation.cubic, 2) |> outlet
}

Sample banks: pitch/velocity zones

A SampleBankVar is a slot for a set of samples with a (pitch, velocity) zone map — the multi-sample instrument counterpart of a single buffer. The bank is described engine-side as a list of zones, each a sound file covering an inclusive pitch range and velocity range (MIDI 0–127) with a root key (the note at which the sample plays back unshifted). Each zone's pitch×velocity rectangle is a tile: no two tiles may cover the same (pitch, velocity) cell, but zones may share a pitch range when their velocity ranges are disjoint — the usual way to build velocity layers — and vice versa. Cells no zone covers read as silence. Like a buffer, the whole bank swaps at runtime without recompiling the synth, and swapping is safe while notes sound.

In the graph, bank lookup(pitch, velocity) resolves one sample of the bank. The lookup runs at Rate.reset — once per note-on inside a voicer (once at init in a non-voicer graph). Its inputs are latched at that moment, so they must be note params, controls, constants, or init-rate values. The result is a BankSample: read it with read/vread exactly like a buffer, and use its metadata accessors to compute the playback rate.

Explicit values always win over the file's.

-- a voicer sampler: each note picks its sample by (pitch, velocity) and
-- plays it at the rate implied by the sample's root key and source rate
fn sampler() S {
    let bank = sampleBankVar();
    voicer(8, fn() S {
        let g = gate();
        let pitch = noteParam("pitch", ControlSpec { lo: 0.0, hi: 127.0, init: 60.0, warp: ControlWarp.linear });
        let vel = noteParam("vel", ControlSpec { lo: 0.0, hi: 127.0, init: 100.0, warp: ControlWarp.linear });
        let h = bank lookup(pitch, vel);
        let rate = ((pitch f64 - (h rootKey) f64) / 12.0) exp2 * (h sampleRate) * (T() f64);
        let d = delayVar();               -- per-voice playhead, zeroed at note-on
        let pos = d read(1);
        (pos + rate) -> d;
        h vread(pos, Interpolation.cubic) f32 * g
    }) sum outlet
}
sampler defSynthX("sampler") await;

]);

-- a looping sampler: sustain loop while the gate is held, run-out on release
fn loopSampler() S {

    }) sum outlet
}

11. Control Flow

Two kinds of conditional exist, and choosing between them matters:

  • select2 / select compute all their inputs every sample and pick one value per channel. Cheap, branch-free, and the right choice for per-sample decisions (they are used throughout common_ugens).
  • if_ / switch generate actual branches in the compiled code: only the taken branch's subgraph runs. Use them when the branches are expensive (whole alternative signal chains) and the condition changes rarely (e.g. a choice control).
FunctionDescription

select(test, exprs)Per-channel N-way select: exprs[test]. All inputs evaluate every sample.

switch(test, funs)N-way branching conditional over an array of subgraph functions, indexed by test.
for_(varname, count, bodyFn)A loop in the generated code: the body subgraph (a fn(S) S receiving the loop variable) runs count times per sample. Prefer ordinary Tzopilotl loops (which unroll into the graph) unless you specifically need a runtime loop.

12. Polyphony: voicer, noteParam, gate

voicer(maxVoices, voiceFn) instantiates maxVoices copies of the voice subgraph, each with independent state (delays, envelopes, random values) and per-note parameters. The voicer's output has one row per voice: a mono voice gives a row of maxVoices channels, which sum mixes to one; a stereo voice gives a maxVoices×2 matrix, which sum(0) mixes to a stereo pair. The engine handles voice allocation, stealing, and note lifetimes.

  • noteParam(name, spec) declares a per-note parameter inside the voice body. The compiled synth gets one input named notes, a matrix with a row per voice; each note parameter is a column of it (a parameter declared with chans > 1 takes that many columns). When a note starts, the engine writes the note's parameter values into its voice's row; parameters the note does not give take their spec's init.
  • gate() reads the per-note gate (column 0 of notes, written by the engine): 1 while the note is held, 0 after note-off. Drive an asr/adsr release from it, or ignore it for one-shot percussive voices (use gate() tr as a trigger and let a decay2 ring out).

Trigger notes from Tzopilotl with the audio_engine bridge: noteOn(nodeID, noteID, params) and noteOff(nodeID, noteID), inside a begin() … sched(silo) bundle like any other command. The params array matches the order in which noteParam is declared in the voice body; gate is not part of it — the engine sets it. noteSetParams(nodeID, noteID, first, values, rampTime) changes a sounding note's parameters from index first, stepped or ramped. The music libraries' player and the app's piano roll drive voicers the same way.

What a note does, at the sample the bundle is scheduled for: the engine picks a voice (the one released longest ago, else it steals the one started longest ago), resets that voice's state — delays, envelopes, filter memory, its random generator — and runs its Rate.reset work, then writes the voice's row of notes. Math that depends only on note parameters is a parameter group per voice (§2.1): it is recomputed when that voice's row changes, and every sample only while one of its parameters is ramping. Voices are computed four at a time where the voice body allows it.

import synthdef.*;
import synthc.compile.*;
import common_ugens.*;
import audio_engine.*;

fn organVoice() S {
    let f = noteParam("freq", ControlSpec { lo: 20.0, hi: 12000.0, init: 440.0, warp: ControlWarp.exponential });
    let a = noteParam("amp",  ControlSpec { lo: 0.0,  hi: 1.0,     init: 0.5,   warp: ControlWarp.linear });
    let g = gate();

    let env = adsr(g, 0.02, 0.1, 0.9, 0.25);

    let harms = [1, 2, 3, 4, 5, 6, 8] vec;
    let amps  = [1.0, 0.7, 0.5, 0.4, 0.25, 0.2, 0.15] vec;
    (f * harms) sinosc * amps |> sum * env * a * 0.18
}

fn organ() S = voicer(8, organVoice) sum outlet;
organ defSynthX("organ") await;
let n = "organ" play;

-- params are [freq, amp] -- declaration order; the engine sets gate
begin(); noteOn(n, 1, [261.6, 0.5]); noteOn(n, 2, [329.6, 0.4]); sched(0);
begin(); noteSetParams(n, 2, 0, [392.0], 0.3); sched(0);   -- glide note 2 up
begin(); noteOff(n, 1); noteOff(n, 2); sched(0);

n stop;
Voice bodies are ordinary subgraphs: they can contain delays, filters, random init-rate values (different per voice), and controls declared outside the voicer are shared across voices. See examples/instrument_synthdefs.x for a set of ten voicer-based instruments (FM bell, pluck, modal bell, kick, snare, …).

Finished voices cost nothing

A released voice keeps sounding until its sound dies away, and the synth stops computing it once it is finished. Until its next note it outputs 0, and its filters, oscillators and random draws are not run. A voice is finished when its gate is off and:

  • the condition it declares with doneWhen holds — x doneWhen(cond) returns x unchanged, so it can end a chain: osc * env doneWhen(env <= 0); or
  • when it declares none, its output has stayed below −120 dB for the voicer's third argument, silence, in seconds (default 0.2: longer than the period of any audible pitch, so the dips of a tremolo don't end a voice): voicer(8, organVoice, 0.5).

voicer(n, body, 0.0) turns this off entirely, doneWhen included. With a few cheap voices, the per-sample checks can cost more than skipping saves.

14. Compiling, Tagging, and Playing

defSynthX

defSynthX(synthFun, name) and defSynthX(synthFun, name, tags) (from synthc.compile) run your graph function, compile the graph with synthc — the Tzopilotl-hosted synthdef compiler — and load the resulting plugin into the engine under name. This is the production path.

defSynthX is async: the clang invocation that builds the .dylib runs on a background worker, so sequences that are already playing keep playing while a def compiles. The call returns a Future<String> holding the generated C++ source; when it resolves, the def has been compiled, loaded, and registered. A failed compile panics: the error prints and the script halts, so code never sails past a def that did not load. Two usage patterns:

  • First definition: await before playing the def — mySynth defSynthX("mySynth") await; — so the def exists when the first note asks for it.
  • Redefinition: just call it, no await. Nodes already running the def keep the code they were created with (the engine keeps the superseded build loaded until its last node is freed); nodes created after the new build loads — the next play, a sequence player's next note — use the new version. Live iteration on a synth never interrupts the music, and a running sound changes only when you tell it to: use a live.proxy (ndef / <-) to crossfade a running node into a new definition.

Inside a non-real-time render script the compile runs synchronously (the render cannot proceed without the def), so the returned future is already resolved.

defSynthXChecked is the fallible form for code that must tolerate and report failures rather than halt (test harnesses that sweep many defs): it returns a Future<Result<String, String>> — ok(cpp) on success, err(message) on a failed analysis, compile, or load — and prints nothing.

synthc writes the plugin as C++ and builds it with the system clang. The generated source is the string the future holds, and is also written to ~/tzpl-build/cpp/, which helps when a synth does not sound as expected.

Tags

Tags are free-form category strings attached to a def (defSynthX(f, "name", ["example"])) that the plugin browser uses for filtering. The TZPL_DEFAULT_TAGS environment variable (comma-separated) appends session-wide default tags to everything compiled — test harnesses set TZPL_DEFAULT_TAGS=test so their defs are born filtered out.

Band-limited wavetable oscillator: osc

osc(b, fm, pm = 0, tableLen = 16384, numTables = 30, interp = linear) is a band-limited wavetable oscillator in the tradition of SAPF's Osc family and SuperCollider's Osc. The BufferVar b holds a bank of numTables wavetables of tableLen samples, one per 1/3 octave, each holding a progressively band-limited copy of the waveform; the oscillator picks the table from its playback frequency so the top partial always stays below Nyquist — a full-spectrum saw with no aliasing at any pitch. Banks are generated by the wavetables module (from a partial list — oscTables(amps, phases, smooth, ...) — or the presets sawTables(), squareTables(), triTables()) and pushed into the buffer with fillBuffer. Table generation runs through the ifft builtin, so it is NRT — build banks at patch-build time.

The smooth parameter mitigates the Gibbs phenomenon. Each band-limited table is a truncated Fourier series, and with a brickwall cutoff (smooth = 0) a truncated series overshoots by about 9% at any discontinuity in the ideal waveform and rings with ripple beside it; adding more partials squeezes the ripple closer to the edge but never shrinks the overshoot. On a saw or square table this appears as a spike and ringing at each jump — and since tables are normalized to their peak, the overshoot also costs headroom. smooth > 0 replaces the brickwall with a gradual spectral rolloff (partial j of a table with band limit h is scaled by cos(π/2 · j/h)^smooth, as in SAPF), fading the series out instead of chopping it: the overshoot and ripple are suppressed at the cost of slightly duller top partials. Values around 1–2 work well for edgy waveforms; 0 keeps the full brightness of an exact truncation.

Like SAPF, one osc front end dispatches on its inputs at graph-build time: with a constant frequency the table-selection math is constant-rate (evaluated once at init) and a single table is read; with a moving frequency the table is re-selected every sample and the two adjacent tables are crossfaded through a smooth curve so table transitions don't tick. A constant pm is the initial phase; a signal pm is per-sample phase modulation in cycles. interp may be none, linear, or cubic (the bank's guard samples don't cover the wider lagrange/sinc kernels).

-- an alias-free saw at any pitch
fn sawOsc() S {
    let b = bufferVar();
    let f = control("freq", ControlSpec { lo: 20.0, hi: 10000.0, init: 110.0, warp: ControlWarp.exponential });
    b osc(f) * 0.2 |> outlet
}
